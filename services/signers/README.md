# Alloc-X Independent Signers

This service is the signing boundary for XRPL settlement. The execution signer,
policy signer, and recovery signer must be deployed as separately authenticated
workloads, each with a distinct non-exportable KMS or HSM key reference.

## Control model

1. A verified security decision and a fully prepared transaction are converted to
   one immutable signing envelope.
2. Each signer verifies the envelope digest, transaction digest, network, fee,
   expiry, and every protected transaction field before calling its key provider.
3. Each partial signature is bound to that envelope. The assembler requires both
   execution and policy roles, as well as the configured XRPL quorum.
4. The XRPL signer list provides an external enforcement point: the treasury
   account cannot settle with one partial signature.

The local development provider exists only to exercise the boundary with
ephemeral non-production wallets. It must not be selected in a deployed
environment. Production providers implement `XrplSigningKeyProvider` with a
KMS/HSM signing API; they do not expose a seed, private key, or key-export API.

## Provisioning and rotation procedure

1. Generate a new signer key inside the isolated key service and record only its
   public XRPL address and key reference in the deployment configuration.
2. Have two authorized operators review the signer-list transaction generated by
   `signerListSetTransaction`; confirm the new policy and execution identities,
   quorum, and recovery address out-of-band.
3. Submit and validate the replacement `SignerListSet` through a controlled
   bootstrap ceremony. Verify the validated signer list from an independent
   read-only ledger monitor.
4. Health-check the new signer with a non-settling signing-envelope exercise,
   then revoke the old KMS/HSM key. Retain signer audit records and the list
   replacement transaction hash.

## Recovery procedure

The recovery signer is a separately held identity, not an application fallback.
It can participate in a preconfigured quorum after an incident is declared. A
recovery action requires the same immutable signing envelope and must be logged.
If a signer is suspected compromised, freeze settlement upstream, rotate the
signer list using the remaining authorized quorum or controlled bootstrap key,
and reconcile all treasury activity before re-enabling execution.

## Deployment boundaries

- One signer service instance per role; no shared runtime, credential, or log
  sink with the application or other signer.
- Key providers may sign but cannot submit XRPL transactions. The later payment
  orchestrator will submit only the assembled blob.
- Do not log envelopes containing operational data beyond their digests. Do not
  log request bodies, blobs, seeds, private keys, or KMS signing responses.
- Main-network activation remains gated by the security assessment and controlled
  rollout controls in the engineering backlog.
